# ADR-007: `gitsafe` を PATH ラッパにしない（強制経路を明示 opt-in に留める）

> 決定: 2026-09-06 / Status: 採用 / 関連: [coordination-spec.md §4.4](./coordination-spec.md), PR #45, `tools/gitsafe`

---

## 文脈

[`tools/gitsafe`](../tools/gitsafe) は、パス claim では表現できない git の共有物（stash / worktree / refs / remote）を守るラッパである（[coordination-spec.md §4.3–4.4](./coordination-spec.md)）。導入の直接のきっかけは、兄弟 worktree で `git stash pop` を実行したセッションが別セッションの退避作業を消費した事故だった。

現在の配備方法は**明示 opt-in** の 2 通りだけである:

```sh
gitsafe git <args...>            # 明示的に前置きする
git() { /path/to/tools/gitsafe git "$@"; }   # シェル関数で `git` を覆う
```

[§10「意図的に対象外」の表](./coordination-spec.md)には「`command git` / 絶対パスで抜けられる。PATH 上の git がラッパである前提を敷く以上のことはしない」と書いてあるが、これは限界の注記であって決定の記録ではなかった。「では PATH ラッパにすべきか」は未決のまま残っていた。本 ADR はそれを決める。

### 隣接プロジェクトの実測

同じ形の問題を、別の目的で解いている個人プロジェクトがある（非公開）。そちらは GitHub アカウントの安全（403 が返る write を連打しない）を目的とした `ghsafe` というラッパで、**素朴に `gh` を PATH ラッパにすると壊れる 3 点を実測で記録している**。参照リンクは非公開なので、要点をここに書き写す:

| 実測された壊れ方 | 原因 |
|---|---|
| read を含む**全ての呼び出しが失敗**した | ラッパが内部で呼ぶ `gh` が PATH 経由でラッパ自身に戻り、自分の single-flight ロックに当たった（自己再帰） |
| 色・ページャ・対話モードが壊れた | 検知のため出力を `"$@" 2>&1 \| tee` で捕獲しており、パイプによって子から見た stdout が tty でなくなった |
| 並列に呼ぶスクリプトが失敗した | 単なる閲覧にも single-flight とレート制限が掛かった（read への巻き添え） |

対処として、argv[0] で振る舞いを変える方式、**inode による自分自身の除外**（パス文字列比較では symlink の経路差で自己除外を素通りする）、stdout は端末へ素通しし stderr だけ複製する形（`{ "$@" 2>&1 1>&3 | tee "$out" >&2; } 3>&1`）が要ることが分かっている。さらにそのプロジェクトは、`gh` のラッパは配備しつつ **`git` のラッパは実装済みのまま意図的に配備していない**。理由は「`git` はあらゆるツールが呼ぶため影響範囲が桁違い」である。

同種の欠陥は本リポジトリでも 1 件出ている。PR #45 のクロスレビューで、`git -C <dir> push` のようにグローバルオプションが先行するとサブコマンド判定が不発になり**ガードを素通ししていた**ことが分かり、修正した。判定を `$1` 決め打ちにしない、という同じ教訓である。

## 決定

**`gitsafe` は明示 opt-in（前置き、またはシェル関数）に留め、PATH に `git` という名前のラッパを置く方式は採らない。**

シェル関数版を推奨形として `deploy/DEPLOYMENT.md` §3.6 に載せる現状を維持する。実装上も argv[0] 分岐を足さない。

## 理由

### 1. 失敗の重さが違う

`ghsafe` が防ぐのはアカウント停止であり、起きたら**復旧に日単位**かかり、その間あらゆる repo の push が止まる。手段は appeal しかなく、**自分では戻せない**。

`gitsafe` が守るものは資源ごとに性質が違うので、雑に「局所的」と括らずに並べる（範囲は [§4.3](./coordination-spec.md) の定義に従う）:

| 資源 | 被害の範囲 | 自力で戻せるか |
|---|---|---|
| `worktree` | その checkout のみ | **戻せない。** `reset --hard` / `clean` が捨てた未コミット・未追跡の内容は、git のどこにも残らない |
| `stash` | 同じ `.git` の全 worktree | 当面は戻せる（上記の prune までの猶予） |
| `refs` | 同じ `.git` の全 worktree（**その clone 内**） | ブランチは概ね戻せる（ローカル reflog）。**タグは既定で reflog を持たない**ので、上書き・削除すると戻せないことがある |
| `remote` | **その repo の全 clone・全 host** | **保証はない。** リモート側の reflog は読めず、古い ref を持つ clone が残っているかどうかに依存する |

つまり「範囲が広いほど重い」ではない。範囲が最も狭い `worktree` は**確実に戻せない**部類であり、範囲が最も広い `remote` は他 clone が残っていれば戻せるが、それは運用状況次第で保証ではない。**範囲と回復可能性は独立している**、というのがここで押さえたい点である。

それでもアカウント停止との差は残る。`gitsafe` の事故はどれも**特定 repo の内容の問題**であって、他の全 repo に対する操作能力を失うものではない。この差が、後述する強制の対価をどこまで払うかの基準になる。

なお「誤って drop しても commit はオブジェクトストアに残る」は**当面の話であって保証ではない**。drop 後の stash commit は到達不能オブジェクトになり、しばらくは `git fsck --unreachable` で拾えるが、`git gc` の prune 対象である。実測では `git reflog expire --expire-unreachable=now --all` に続けて `git gc --prune=now` を掛けると回収不能になった。回復可能性は事故の重さを下げるが、消せない差ではない。

### 2. いまは自己再帰しない。PATH ラッパにすると自分で壊す

`gitsafe` の内部呼び出しは `command git` である。`command` はシェル関数を迂回するので、**シェル関数版では自己再帰が構造的に起きない**。これはタダで手に入っている性質である。

一方 `command` は **PATH 探索は迂回しない**。`~/bin/git` がラッパなら `command git` はそのラッパを見つけ、上表 1 行目の自己再帰に落ちる。PATH ラッパ化とは、いま無料で成立している不変条件を壊し、inode による自己除外で作り直す作業に等しい。

### 3. ネットワーク依存を無関係なリポジトリへ広げる

ガード対象の操作は `GET /coordination/git/guard` に照会する（タイムアウト 5 秒）。到達不能なら stash タグのみに縮退するが、**到達できてエラー応答なら拒否する**（エラーを許可と見なさないため）。

正確に言えば、この依存は**シェル関数を `.zshrc` に置いた時点で既にそのシェル全体に掛かっている** — 無関係な repo での `reset --hard` も照会する。PATH ラッパ化が新たに広げるのは、**そのシェルを経由しない呼び出し**である。エディタの git 統合、ビルドスクリプト、`cron`、他ツールが子プロセスとして起動する `git` が、すべてボードの可用性に依存するようになる。ここが質的な差で、**人が打っていない git まで調整ボードの障害で止まる**のは対価として重い。

シェル関数側の依存が気になるなら、対処は PATH ラッパではなく逆向き（関数の適用範囲を絞る、後述の中間案）である。

### 4. tty は現状壊れていない。壊す変更を先に入れる理由がない

`gitsafe` は出力を捕獲せず `real_git` をそのまま呼ぶため、色・ページャ・対話がそのまま通る。上表 2 行目の問題は**まだ持っていない**。PATH ラッパ化それ自体は tty を壊さないが、「全 `git` が経路に乗る」状態は出力捕獲の誘惑と隣り合わせであり、そこを踏むと影響範囲は全リポジトリになる。

### 5. 迂回可能性は、この層では欠陥ではない

`gitsafe` の claim は**助言的**である（[§4](./coordination-spec.md)）。守りたいのは「調整に参加している主体が、うっかり他人の共有物を壊すこと」であって、意図的に迂回する主体ではない。意図的な迂回を守備範囲に入れるなら、必要なのは PATH ラッパではなく、そもそも共有 clone をやめることである。

## 不採用にした代替案

| 案 | 不採用の理由 |
|---|---|
| `~/bin/git` に PATH ラッパを置く | 上記 1〜4。とくに影響範囲が全リポジトリ・全ツールに広がる |
| git hooks で強制する | `git stash pop` に対応するフックが存在しない。事故そのものを構造的に覆えない |
| ガードを fail-closed にする（`AXONRELAY_URL` 未設定を拒否し、到達不能でも拒否する） | **守りは増える**（下記参照）が、可用性の対価が現時点では見合わない |
| 出力を tee して検知に使う | いま tty が壊れていない。検知したいものが無い（`gitsafe` は事前照会型で、事後の出力解析に依存していない） |

### ガードの fail-closed 化について

この案は**守りを実際に増やす**ので、そこを曖昧にしないでおく。オフラインで効くのは stash 所有者タグだけであり、ボードに照会できないとき `reset --hard` / `clean` / `branch -D` / force-push は**無条件に通る**。

ここは 2 つの別々の変更であることに注意する。現行実装は次のように分かれている:

| 状態 | 現行の挙動 | fail-closed 化に必要な変更 |
|---|---|---|
| `AXONRELAY_URL` 未設定 | 照会をスキップして許可 | 未設定を拒否する |
| URL は設定済み、`curl` が失敗（到達不能） | 縮退して許可 | 到達不能でも拒否する |
| 到達できて 4xx/5xx | **既に拒否**（エラーを許可と見なさない） | 変更不要 |

つまり「必須化」だけでは到達不能時の穴は塞がらない。守りを実際に増やすには**両方**が要る。

それでも今は採らない。理由は 2 つある。第一に、本ラッパを作らせた事故は stash の消費であり、そこはオフラインでも塞がっている。第二に、ボード不達で `reset --hard` が止まる状態は、調整に参加していない作業まで止める（上記 3 と同じ性質）。**stash 以外の資源が実際に事故を起こしたら、この判断を先に見直す。** PATH ラッパ化より順序が先である。

## 採用しうる中間案（今回は実施しない）

**参加する clone に入ったときだけシェル関数を有効にする。** ディレクトリ移動フック（`zsh` の `chpwd` 等）で、共有 clone の下にいる間だけ関数を定義・解除すれば、「全 `git` を覆う」ことなく「その clone では付け忘れない」に近づく。

ただしこの案には限界が 3 つある。

1. **素の `direnv` ではできない。** `direnv` が親シェルへ反映するのは環境変数であって関数定義ではないため、別の仕組みが要る。
2. **対話シェルからの呼び出ししか覆わない。** エディタやスクリプトが子プロセスとして起動する `git` は通らない。
3. **判定軸がずれる。** 有効・無効を決めるのはシェルの現在地であって、git が実際に触る repo ではない。`gitsafe` は `git -C <dir>` を扱えるので、参加 clone の中から `git -C /other/repo reset --hard` を打てば**無関係な repo に対してガードが掛かり**、逆に外から `git -C /participating/clone stash pop` を打てば**守りたい対象を素通しする**。正しくやるなら、現在地ではなく操作対象の repo を見て有効化する必要がある。

したがって「PATH ラッパの利点の大半が得られる」とは言えない。得られるのは「参加 clone の中で人が対話的に打つ `git` の付け忘れ対策」だけである。共有 clone の運用が定着し、付け忘れが実際に事故を生んだ時点で、この限定的な効果で足りるかを含めて検討する。

## 影響

- [coordination-spec.md §10](./coordination-spec.md) の out-of-scope 表の該当行は、本 ADR を決定の出典として参照する
- `deploy/DEPLOYMENT.md` / `deploy/DEPLOYMENT.ja.md` §3.6 の導入手順は変更しない
- 見直しの条件は 3 つ。**(a)** シェル関数の付け忘れに起因する事故が実際に起きたとき（まず中間案を検討する）。**(b)** stash 以外の資源（worktree / refs / remote）で事故が起きたとき（PATH ラッパ化より先に、未設定と到達不能の両方を拒否する fail-closed 化を検討する）。**(c)** `gitsafe` が事前照会型をやめ、出力の事後解析を必要とするようになったとき（そのときは上表 2 行目の tty 対処が要る。3 行目の read への巻き添えは single-flight とレート制限を持つ実装の話で、`gitsafe` はどちらも持たないため該当しない）
