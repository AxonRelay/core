# ADR-013: MCP 2026-07-28 の対話モデルへの移行と互換性マトリクス

- Status: Accepted (2026-09-08)
- Issue: #30（Epic #32 配信順序 4）
- 関連: [ADR-009](./adr-009-artifact-commitment.md)、[ADR-011](./adr-011-caller-identity.md)、
  [docs/mcp-server.md](./mcp-server.md)、migration `013`

## 文脈

`review_pending_task` は tool 実行の途中で人間に問いを出し、答えを待って台帳に
記録する。この「途中で問う」仕組みが MCP 2026-07-28 改訂で変わった。

- **2025-11-25 まで** — サーバは開いている接続に `elicitation/create` を単発の
  server→client リクエストとして送り、`tools/call` はその場で止まって答えを待つ。
  接続が切れれば判断は失われる。
- **2026-07-28 から** — `tools/call` は `InputRequiredResult` を**返す**。そこには
  問いと、不透明な `requestState` ハンドルが入っている。クライアントは答えと
  ハンドルを添えて**同じ tool をもう一度呼ぶ**。判断は再開可能になり、そのかわり
  tool 本体はラウンドごとに走る。

AxonRelay の実装は前者を直接呼んでいた（`ctx.elicit(...)`）。SDK はこの呼び出しに
バージョンガードを持たないので、新しい改訂を交渉したクライアントに対しても単発
リクエストを送る。承認の挙動がクライアントと SDK の版に依存する、という状態だった。

同時に、後者の「呼び出しごと再送される」という性質は台帳にとって新しい危険でもある。
再送は正常系である（応答を取りこぼしたクライアントの再試行）。tool 本体が二度走れば
承認エントリが二つ入りうる。**重複しうる承認台帳は、何が決まったかの記録ではない。**

## 決定

### 1. どちらの形にするかは SDK に決めさせる

問いを直接送るのをやめ、SDK のリゾルバ（`Resolve` / `Elicit`）で宣言する。
交渉した改訂が求める形——MCP 2025-11-25 までは単発リクエスト、MCP 2026-07-28 からは
`InputRequiredResult` + `requestState`——に SDK が描き分けるので、実装は一本になる。

手で分岐しない理由は単純で、分岐した瞬間に片方だけがテストされるからである。

### 2. 表示した artifact をラウンドをまたいで固定する

`_shown_artifact` リゾルバが、問いを組み立てる前に決定対象の draft を 1 個の値として
固定する。問いはその値から描かれ、tool 本体が判断を束縛するのも同じ値である。
「表示したもの」と「記録するもの」が二回の読み取りではなく一つのオブジェクトになる。

これが効くのは、SDK が記録済みの回答を**問いの描画そのもの**に紐づけているためで
ある。draft が差し替われば問いの文面が変わり、記録済みの回答は破棄されて新しい
draft について**もう一度尋ねられる**。ADR-009 の「見ていない内容を承認しない」が、
接続をまたいでも成立する。

### 3. 再送は台帳の側で吸収する（migration 013）

`approvals.decision_key` が「この draft に対するこの判断」を一意に名指す。キーは
task / 版 / commitment / 可否 / コメント / 編集内容に加えて、**記録先の reviewer**
から導かれる。reviewer を入れるのは、1 つの task に複数の承認権者がありうるからで
ある（`check_may_approve`）。同じ draft に同じ判断・同じ文言で至った別人は 2 件の
エントリであって 1 件ではない——「誰が何を承認したか」が主題の台帳で、2 人目の判断を
黙って捨てて 1 人目のエントリを返すのは、最悪の冪等性である。編集内容は**承認のとき
だけ**キーに入る。差戻しでは `_apply_decision` が編集を捨てるので、入れると無視される
値の違いで同一の差戻しが 2 件記録されてしまう。

`record_approval` は task 行ロックの下でキーを引き、既にあればその行を返して**何も
追加しない**——承認も、編集が作るはずだった draft 版も。`(task_id, decision_key)` の
unique index は、ロックをすり抜けた二重書き込みの最後の砦である。

`record_approval` は既存の行を**返さず例外にする**（`DuplicateDecisionError`）。
返してしまうと、呼び出し元は「自分が書いた」と「既に誰かが書いていた」を区別できない。
ロックの内側で 1 つだけが「書いた」と告げられ、もう一方は resume せずに記録済みの
判断を返す。

キーは**ハッシュの中**に入れる（payload v3）。「リクエストを名指すだけだから外でよい」
と最初は考えたが、それは誤りだった。判断そのものを書き換えるコストは「以降の全エントリの
再計算」である。サーバが**動作の根拠にする**フィールドが payload の外にあると、その
コストがゼロになる——`decision_key` を消せば重複排除は無効化され、検証は valid のまま
になる。これは程度ではなく種類の違いなので、v1→v2 と同じやり方（`hash_version` を行ごとに
見る）で v3 にした。既存の v1 / v2 行は書かれたとおりに検証され、変わらない。

**1 つの問いに判断は 1 つ。** キーが吸収するのは「同じ判断の再送」だけで、**別の**
判断が同時に来る場合は守らない。surface がロックの外で `WAITING_APPROVAL` を見てから
記録すると、2 人がともに通り、2 件とも記録され、2 件とも resume される——2 件目は
下の段落のとおり誰も見ていない問いに答える。そこで surface は `record_approval` に
`claim_waiting=True` を渡し、**task 行ロックの下で**（キーの照合の後に）状態を確かめ、
エントリと同じコミットで task を `APPROVED` / `REJECTED` に移す。2 人目は
`DecisionNotOpenError` で止まり、resume しない。配送が失敗したときの扱いは、
失敗が送信前かどうかで分ける。Platform 未設定（何も送っていない）なら `reopen_decision` が
すぐ `WAITING_APPROVAL` に戻す——その判断がまだ最新のエントリである場合に限る。それ以外の
失敗は受理後のタイムアウトと見分けがつかないので**何も仮定しない**: thread の状態を読んで
投影し、Platform が「人を待っている」と言うときだけ `WAITING_APPROVAL` になる。読めない
とき・キャンセルされたときは `APPROVED` / `REJECTED` のまま新しい判断を受け付けず、
`refresh_task`（REST は `POST /tasks/{id}/refresh`）が読み直すまで待つ。Platform の状態はネットワーク越しにロックなしで読む（同期の行ロックを await をまたいで持つと worker が止まりうる）。順序は `tasks.state_version` で決める: 判断の記録・開け直し・投影のたびに増え、snapshot は**読み始めたときの版のまま**であるときだけ、ロックの下で 1 トランザクションで反映される。配送成功時の結果も同じで、その判断が残した版にしか載らない。だから 2 つの読み直しが逆順にコミットしても、遅れて届いた配送結果でも、古い「待機中」が新しい状態を上書きしない。盲目的に開け直すと、
graph がすでに先へ進んでいた場合に 2 件目の判断がその先の問いに答えてしまう。
これで下に書く「人が送り直す」経路が、graph の実際の状態に基づいて残る。`tasks.status` はハッシュの外の可変列だが、
書き換えて得られるのは「もう 1 件判断を**記録できる**」ことだけで、記録済みの判断を
変えたり消したりはできない。

**束縛した再送の残余。** credential による判断は版か commitment を名指す（ADR-011）ので、
応答を失った再送は、graph が新しい draft を出していれば stale として拒否される。同梱の graph
は差戻しのたびに writer が新しい draft を足すので、通常はこれで足りる。例外は writer が
**バイト単位で同じ文面**を返した場合で、投影は同一内容を新しい版にしない。このとき再送は
通り、2 件目の判断として記録・配送される。ただし、その判断が当たるのはレビュアーが実際に
見たのと同じバイト列であって、誰も見ていない成果物ではない。これを塞ぐには直接 tool にも
キーか台帳先頭の CAS を要求する必要があり、「同じ文言の新しい判断」を記録する逃げ道
（上の段落）と衝突するので、今は採らない。

**graph への配送はやり直さない。** `resume_thread` は LangGraph の素の resume で
idempotency key を取らない。2 回目は「同じことの繰り返し」ではなく、**そのとき graph が
到達している interrupt に答えてしまう**——誰も見ていない問いへの判断になりうる。しかも
Platform が受理した後のタイムアウトと受理されなかったケースは区別できないので、自動
再送はまさにその区別を当てずっぽうでやることになる。

したがってサーバが負うのは再送ではなく**正直な報告**である: 判断は台帳にある、graph は
確認していない、必要なら `approve_task` / `reject_task` で人が送り直せる。それは 2 件目の
エントリを作るが、それが事実である——誰かが「もう一度送る」と決めたのだから。

自動復旧は一度実装して**取り下げた**。それを安全にするには配送状態を表す可変列が要り、
可変列はハッシュに入れられず、入れられない列をサーバの動作の根拠にすると上と同じ
「コストゼロで動作を変えられる」穴になる。塞ぐには配送試行の追記専用チェーン——2 つ目の
台帳——が要る。稀な Platform の失敗を自動で癒すために台帳をもう 1 本持つのは、この
リポジトリが守ろうとしている性質に対して割に合わない。人が既存の tool で送り直せる。

### 4. ハンドルは封をして期限を切る

`requestState` はクライアントを経由して戻ってくる。SDK はこれを攻撃者の制御下に
ある値として扱い、自分が発行したものだけを受け入れる。鍵は既定でプロセスローカル
（再起動をまたぐと問い直しになる。stdio サーバはクライアントと運命を共にするので
これが正しい既定）、`AXONRELAY_REQUEST_STATE_KEY` を設定すると複数ワーカーと再起動を
またいで再開できる。TTL は 15 分——人間が draft を読む時間としては十分で、漏れた
ハンドルが恒久的な承認権にはならない長さ。

弱い鍵は起動時に環境変数名を挙げて拒否する。

ハンドルは**それを発行した呼び出し元に束縛する**。SDK 既定の束縛は SDK 自身の OAuth
コンテキストを読むが、AxonRelay は呼び出し元を自前で解決する（ADR-011）ためそれは
常に空で、放置すると全ハンドルが無束縛になり、A に表示された draft のラウンドを B が
引き取れてしまう。提示された Authorization ヘッダのダイジェストを束縛値に使う——
1 回の呼び出しのラウンド間で安定し、別の呼び出し元では異なり、平文ではない。stdio と
無提示の HTTP では `None`（loopback 前提）で、SDK はラウンド間で束縛の有無が変わる
ハンドルを拒否するので両者が混ざることはない。

### 5. 対話できないクライアントには経路を告げる

判断できない呼び出し元には、**draft を見せる前に**断る。`check_may_approve` を
`_shown_artifact` の中——問いが組み立てられる前——に置く。答えが返ってきてから
「あなたには承認権がない」と言うのは拒否ではない。その時点で内容はもう wire に出て
いる。同じ理由で、再送応答を返す経路もこのチェックの後ろに置く。

form elicitation を宣言していないクライアントには**何も尋ねない**。
`status="elicitation_unsupported"` と、そのまま使える `artifact_version` /
`expected_commitment`、そして `approve_task` / `reject_task` の名前を返す。
束縛の保証は同じで、対話のラウンドだけが無い。

### 6. 主張はデータとして持つ

対応する仕様改訂・SDK 版・検証済みクライアントを `backend/app/mcp/compat.py` に
置き、`axonrelay://compat` として配信する。テストが SDK の対応版集合と突き合わせる
ので、SDK が改訂を増やしても減らしてもここで落ちる。散文の互換性表は古びるが、
これは古びない。

## 帰結

- 承認は 2024-11-05 から 2026-07-28 まで、stdio と Streamable HTTP の両方で動く。
  `backend/tests/test_mcp_protocol_compat.py` が両方の対話モデルを実際のワイヤ上で
  走らせる（HTTP 側は実際に uvicorn を上げる。旧モデルは server→client の逆方向
  チャネルを要求するので、ストリームしないテスト用トランスポートでは検証できない）。
- 承認 1 件につき台帳エントリ 1 件・graph resume 1 回が、再送があっても保たれる。
- 判断が通って task が承認待ちを離れたあとの再送は、`_shown_artifact` が先に止める
  ので `status="stale_decision"` になる。文面はどちらにも踏み込まない——「このラウンドは
  何も記録していない」は常に真だが、「何も記録されていない」は偽（1 回目が立って
  いる）だし、「あなたの判断が立っている」も偽でありうる（別の誰かが先に task を
  動かした場合）。確実なことだけ言い、残りは `get_task` / `verify_task_ledger` を
  見よと案内する。
- 配送が確認できなかった場合、サーバは何もしない。`ToolError` で状況を伝え、人が
  `approve_task` / `reject_task` で送り直す。これは main の現状と同じ回復経路であり、
  `decision_key` はその上で再送の重複だけを防ぐ。
- ledger の運用列はこの 1 本（`decision_key`）だけで、それはハッシュの中にある。
  検証が見られない列をサーバの動作の根拠にしない、というのが結論である。
- `review_pending_task` が「承認待ちでない」ときにエラーではなく
  `status="stale_decision"` を返すようになった。これは競合の通常の結末であり、
  回答ラウンドでも起こりうる。`approve_task` / `reject_task` は従来どおりエラー。

## 却下した選択肢

- **改訂ごとに手で分岐する。** 片方だけがテストされる。SDK がすでに正しく分岐する。
- **単発 elicitation のまま据え置く。** 新しい改訂のクライアントで承認が
  クライアント実装依存になる。issue #30 が挙げた問題そのもの。
- **再送検知を `request_state` に紐づける。** 台帳が MCP の内部形式に依存する。
  判断の内容から導いたキーなら、どの経路から来た再送でも同じ答えになる。
- **タスクの状態遷移だけで二重記録を防ぐ。** 差戻しは承認待ちのまま戻ることがあり、
  そこでは同じ draft への二度目の書き込みを止められない。
